# 띵타이쿤 재배전문가 요리 수익 계산기 설계

## 1. 목적

사용자가 재료별 조달 방식과 구매 가격을 입력하면 현재 3일 가격 주기의 모든 요리 수익을 다시 계산하고, 어떤 요리를 만드는 것이 가장 유리한지 근거와 함께 추천한다.

서비스는 PC 사용을 우선하되 320px 이상의 모바일 화면에서도 핵심 추천, 재료 가격 수정, 사용자 설정 확인이 가능해야 한다.

## 2. 성공 기준

- 사용자는 회원가입하지 않고 바로 계산기를 사용할 수 있다.
- 사용자가 재료 가격이나 조달 방식을 변경하면 모든 요리 결과가 즉시 갱신된다.
- 추천 결과에는 판매가뿐 아니라 구매비용, 직접 준비할 재료, 순이익, 수익률이 함께 표시된다.
- 관리자는 3일마다 새로운 스킬 미적용 요리 기준 가격을 일괄 등록하고 게시할 수 있다.
- 게시 기간이 끝난 가격은 현재 가격으로 오인되지 않도록 만료 상태가 표시된다.
- 가격이나 레시피가 누락된 요리는 추정값으로 순위를 만들지 않고 계산 불가 사유를 표시한다.

## 3. 첫 버전 범위

### 포함

- 재배전문가 요리와 중간재 레시피
- 재료별 `직접 수확`, `전부 구매`, `혼합` 조달 방식
- 구매 묶음 수량과 총가격 입력 및 개당 가격 환산
- 보유 수량을 제외한 부족 수량 계산
- 현재 3일 가격 주기의 스킬 미적용 요리 가격
- 수익에 직접 영향을 주는 전문가 스킬
- 요리별 재료비, 판매금액, 순이익, 수익률
- 전부 구매 기준과 사용자 실제 조달 기준의 추천 순위
- 가격 주기 관리자 화면과 변경 이력
- IndexedDB에 사용자 설정과 가격 자동 저장
- 사용자 데이터 JSON 내보내기와 가져오기

### 제외

- 일반 사용자 회원가입과 기기 간 동기화
- 사용자 간 공동 시세 제보
- 게임 화면 OCR 및 자동 데이터 수집
- 재배 이외의 전문가
- 판매 완료 가능성 예측
- 유통기한 손실률
- 시설 병렬 처리와 시간당 수익 최적화
- 직접 수확 재료의 기회비용 계산

## 4. 사용자와 권한

### 일반 사용자

- 인증 없이 게시된 공통 데이터를 읽는다.
- 전문가 스킬, 재료 가격, 보유량, 조달 방식, 즐겨찾기를 자신의 브라우저에 저장한다.
- 서버 공통 데이터는 수정할 수 없다.

### 관리자

- Supabase Auth로 로그인한다.
- 아이템, 레시피, 스킬 효과, 가격 주기, 요리 가격을 생성하거나 수정한다.
- 가격 주기를 초안으로 저장하고 검증한 뒤 게시한다.
- 모든 변경에는 변경자, 변경 시각, 변경 사유가 기록된다.

## 5. 기술 구조

- 프레임워크: Next.js App Router + TypeScript
- 스타일: CSS Modules와 전역 디자인 토큰
- 서버 데이터: Supabase PostgreSQL
- 관리자 인증: Supabase Auth
- 사용자 로컬 데이터: IndexedDB
- 데이터 검증: Zod
- 단위 및 통합 테스트: Vitest
- 컴포넌트 테스트: React Testing Library
- 브라우저 핵심 흐름 테스트: Playwright
- 배포: Vercel과 Supabase

계산 엔진은 React 컴포넌트나 Supabase에 의존하지 않는 순수 TypeScript 모듈로 구현한다. 같은 입력은 항상 같은 결과를 반환하고, UI와 관리자 기능은 이 모듈의 공개 인터페이스만 사용한다.

## 6. 화면 구조

### 공통 탐색

PC에서는 좌측 탐색과 본문을 함께 표시한다.

- 오늘의 추천
- 재료 가격
- 내 설정
- 요리·레시피
- 가격 변동

모바일에서는 하단에 `추천`, `재료 가격`, `내 설정`을 표시하고 나머지는 더보기 메뉴에 배치한다.

### 오늘의 추천

첫 화면은 입력 양식이 아니라 추천 결과를 먼저 보여준다.

상단에는 현재 가격 주기의 시작·종료 시각, 다음 갱신까지 남은 시간, 데이터 상태를 표시한다. 추천은 두 탭으로 분리한다.

1. **전부 구매 효율**: 입력된 유저상점 가격으로 모든 거래 가능 재료를 구매한다고 가정한다. 재료 가격이 모두 있는 요리만 순위에 포함하며 구매비용 대비 수익률을 기본 정렬로 사용한다.
2. **내 실제 조달**: 사용자가 선택한 직접 수확·구매·혼합 설정을 적용한다. 현금 기준 순이익을 기본 정렬로 사용하고 직접 준비할 재료를 함께 표시한다.

순위 행에는 요리명, 구매비용, 판매금액, 순이익, 수익률, 직접 준비할 재료 수를 표시한다. 사용자는 순이익·수익률·요리명으로 다시 정렬할 수 있다.

### 재료 가격

PC에서는 표, 모바일에서는 재료별 카드로 제공한다. 각 재료에는 다음 필드가 있다.

- 조달 방식: `SELF`, `PURCHASE`, `MIXED`
- 현재 보유량
- 구매 묶음 수량
- 구매 묶음 총가격
- 계산된 개당 가격
- 가격 확인 시각

`SELF`에서는 구매 입력을 숨긴다. `PURCHASE`에서는 필요 수량 전체를 구매 대상으로 본다. `MIXED`에서는 필요 수량에서 보유량을 뺀 부족분만 구매 대상으로 본다.

### 내 설정

첫 버전에는 실제 수익 계산에 직접 필요한 전문가 스킬 레벨만 표시한다. 설정을 변경하면 서버 요청 없이 추천 결과를 즉시 다시 계산한다.

### 요리 상세

- 기준 판매가와 스킬 적용 판매가
- 필요한 최종 재료
- 중간재 제작 트리
- 구매 재료와 직접 준비 재료
- 사용 원가와 실제 묶음 구매 지출
- 구매 후 남는 재료
- 순이익과 수익률
- 계산에 사용한 가격 확인 시각

### 관리자 가격 주기

관리자는 이전 주기 가격을 복사한 뒤 변경된 가격을 수정할 수 있다. 일괄 붙여넣기를 지원하며 저장 단계는 `초안 저장 → 검증 → 미리보기 → 게시` 순서다.

## 7. 디자인 시스템

간결한 정보 도구 형태로 구성하며 장식보다 숫자와 추천 근거의 계층을 우선한다.

- Primary 세이지: `#496B57`
- Secondary 토마토: `#C65A46`
- 기본 배경: `#FAF7F2`
- 기본 글자: `#2D2925`

세이지는 주요 버튼, 선택 상태, 활성 탐색에 사용한다. 토마토는 중요한 변화와 제한된 강조에만 사용하며 오류색으로 사용하지 않는다. 손실과 오류는 별도의 짙은 적색, 경고는 황색 계열을 사용하여 보조색과 의미가 겹치지 않게 한다.

PC에서는 입력 영역과 추천 결과를 동시에 볼 수 있고, 모바일에서는 넓은 표를 카드로 바꾼다. 필수 기능은 hover 없이 사용할 수 있어야 하며 입력 컨트롤의 터치 영역은 최소 44px을 확보한다.

## 8. 서버 데이터 모델

### `items`

- `id`: UUID
- `slug`: 고유 문자열
- `name`: 표시 이름
- `category`: `RAW`, `PROCESSED`, `DISH`, `FIXED_INGREDIENT`
- `tradeable`: 거래 가능 여부
- `active`: 현재 사용 여부
- `source_url`: 공식 근거 URL
- `verified_at`: 공식 자료 확인 시각

### `recipes`

- `id`: UUID
- `output_item_id`: 결과 아이템
- `output_quantity`: 1회 제작 결과 수량
- `active`: 현재 사용 여부
- `valid_from`, `valid_to`: 레시피 적용 기간

### `recipe_ingredients`

- `recipe_id`
- `ingredient_item_id`
- `quantity`

레시피 그래프는 순환을 허용하지 않는다. 관리자 저장 시 결과물에서 다시 자신으로 돌아오는 경로가 발견되면 저장을 거부한다.

### `price_cycles`

- `id`: UUID
- `starts_at`, `ends_at`: Asia/Seoul 기준 적용 구간
- `status`: `DRAFT`, `PUBLISHED`, `EXPIRED`
- `published_at`, `published_by`

주기는 시작 시각을 포함하고 종료 시각을 포함하지 않는 `[starts_at, ends_at)` 구간이다. 종료 시각의 기본값은 시작 시각에서 정확히 72시간 후이며 다른 게시 주기와 겹칠 수 없다.

### `cooking_prices`

- `cycle_id`
- `dish_item_id`
- `base_price`: 스킬 미적용 기준 가격
- `source_note`: 확인 근거

한 주기와 한 요리의 조합은 유일하다.

### `skills` 및 `skill_levels`

`skills`는 이름, 적용 대상, 최대 레벨을 저장한다. `skill_levels`는 레벨별 효과 타입과 수치를 저장한다.

첫 버전에서 지원하는 효과 타입은 다음과 같다.

- `SELL_PRICE_MULTIPLIER`
- `BULK_SALE_MULTIPLIER`
- `EXPECTED_EXTRA_OUTPUT`

효과의 적용 순서와 반올림 방식은 버전이 있는 계산 규칙으로 관리한다. 첫 공개 전에 스킬이 없는 가격과 각 지원 스킬이 적용된 게임 표시 가격을 비교하여 규칙을 검증한다. 검증된 규칙과 일치하지 않는 효과는 활성화하지 않는다.

### `change_logs`

- 대상 테이블과 레코드
- 변경 전·후 JSON
- 변경자
- 변경 사유
- 변경 시각

## 10. 계산 규칙

### 구매 단가

```text
unit_purchase_price = purchase_pack_price / purchase_pack_quantity
```

구매 묶음 수량이나 가격이 0 이하이면 해당 재료 가격은 유효하지 않다.

### 필요한 구매 수량

```text
SELF     = 0
PURCHASE = required_quantity
MIXED    = max(0, required_quantity - owned_quantity)
```

### 요리에 사용된 구매 원가

```text
consumed_purchase_cost = required_purchase_quantity × unit_purchase_price
```

중간재는 레시피 트리를 원재료까지 펼친 뒤 같은 아이템의 필요 수량을 합산한다. 사용자가 중간재 자체의 구매 가격을 입력한 경우에는 `직접 제작`, `중간재 구매`, `더 저렴한 방식 자동 선택` 중 사용자가 지정한 방법을 적용한다.

### 실제 묶음 구매 지출

```text
packs_to_buy = ceil(required_purchase_quantity / purchase_pack_quantity)
cash_outlay = packs_to_buy × purchase_pack_price
leftover_quantity = packs_to_buy × purchase_pack_quantity - required_purchase_quantity
```

추천 순위의 원가와 수익률에는 이번 제작에 실제 소비된 원가를 사용한다. 실제 묶음 구매 지출과 남은 재료는 상세 화면에서 별도로 보여준다. 남은 재료를 자동으로 보유량에 더하지 않으며 사용자가 구매 완료를 눌렀을 때만 반영한다.

### 판매금액

```text
sale_revenue = apply_verified_skill_rules(base_dish_price, skill_profile, sale_quantity)
```

스킬 효과는 검증된 계산 규칙의 순서와 반올림 단계에 따라 적용한다. 기준 가격은 서버의 현재 게시 주기에서 가져온다.

### 순이익과 수익률

```text
net_profit = sale_revenue - consumed_purchase_cost
purchase_roi = net_profit / consumed_purchase_cost × 100
```

구매 원가가 0이면 수익률은 계산하지 않고 `구매비용 없음`으로 표시한다. 직접 수확 재료는 첫 버전의 현금 기준 계산에서 0원이며, 결과에 필요한 종류와 수량을 반드시 표시한다.

### 계산 불가

다음 중 하나라도 해당하면 요리를 순위에서 제외하고 원인을 표시한다.

- 현재 게시된 요리 가격이 없음
- 필요한 구매 재료의 가격이 없음
- 레시피 또는 중간재 레시피가 불완전함
- 지원하지 않거나 검증되지 않은 스킬 효과가 계산에 필요함
- 레시피 그래프에 순환이 존재함

## 11. 가격 주기 운영

- 관리자는 다음 주기의 시작 시각을 입력하며 종료 시각은 72시간 뒤로 자동 제안된다.
- 이전 가격을 복사해 초안을 만든 후 새 가격으로 수정한다.
- 모든 활성 요리의 가격이 있어야 게시할 수 있다.
- 가격은 양의 정수여야 한다.
- 공식 최저·최고 범위를 벗어난 값은 경고하며 관리자가 근거를 입력해야만 게시할 수 있다.
- 게시된 주기는 일반 사용자가 읽을 수 있지만 수정은 관리자만 가능하다.
- 현재 시각이 게시 주기 밖이면 추천 화면 전체에 `이전 주기 참고값` 상태를 표시한다.
- 한 번 게시된 가격을 수정하면 원래 값과 변경 사유를 변경 이력에 남긴다.

## 12. 오류와 복구

- Supabase 조회 실패 시 마지막으로 성공적으로 받은 공통 데이터를 캐시에서 읽고 오프라인·캐시 상태를 표시한다.
- 현재 주기 캐시가 없으면 추천을 만들지 않고 재시도를 제공한다.
- 잘못된 재료 가격은 해당 입력 옆에서 설명하고 다른 정상 입력은 유지한다.
- 관리자 일괄 입력은 행 단위 오류를 모두 표시하고 오류가 하나라도 있으면 게시를 막는다.
- IndexedDB 저장 실패 시 화면 계산은 유지하되 저장 실패를 알리고 JSON 내보내기를 제공한다.

## 13. 보안

- Supabase Row Level Security로 공통 게시 데이터는 공개 읽기만 허용한다.
- 생성·수정·게시는 관리자 역할이 있는 인증 사용자만 허용한다.
- 서비스 역할 키는 브라우저 번들에 포함하지 않는다.
- 관리자 입력은 서버에서 Zod로 다시 검증한다.
- 변경 이력은 일반 관리자 화면에서 삭제할 수 없다.

## 14. 접근성과 반응형 기준

- 모든 입력은 연결된 label을 가진다.
- 키보드만으로 가격 입력, 정렬 변경, 상세 열기가 가능해야 한다.
- 색만으로 추천·손실·만료 상태를 구분하지 않고 텍스트를 병행한다.
- 320px부터 가로 잘림 없이 핵심 기능을 사용할 수 있어야 한다.
- 모바일의 입력 글꼴은 16px 이상으로 유지하여 자동 확대를 방지한다.

## 15. 검증 전략

### 계산 엔진 단위 테스트

- 구매 묶음 단가 환산
- 직접 수확·전부 구매·혼합별 구매 수량
- 중간재 다단계 펼치기와 같은 재료 합산
- 중간재 구매와 직접 제작 비교
- 구매 원가 0일 때 수익률 미표시
- 묶음 구매 지출과 남은 재료
- 누락 가격이 있는 요리 제외
- 레시피 순환 검출
- 검증된 스킬 효과와 판매 수량 조건

### 데이터 통합 테스트

- 현재 시각에 맞는 게시 가격 주기 하나만 조회
- 겹치는 주기 게시 거부
- 일반 사용자의 쓰기 거부
- 관리자의 가격 초안·게시·변경 이력 생성

### 브라우저 핵심 흐름

1. 재료 가격과 조달 방식을 입력한다.
2. 추천 순위가 즉시 바뀌는지 확인한다.
3. 요리 상세에서 재료비 근거를 확인한다.
4. 새로고침 후 로컬 설정이 복원되는지 확인한다.
5. 390px 모바일 화면에서 같은 흐름을 수행한다.
6. 관리자가 새 가격 주기를 게시한 뒤 일반 화면이 새 주기를 사용하는지 확인한다.

## 16. 출시 승인 조건

- 활성화된 모든 요리의 레시피와 현재 기준 가격에 공식 출처와 확인일이 있다.
- 지원하는 각 판매 스킬 조합의 계산 결과가 실제 게임 표시 가격과 일치한다.
- 계산 불가 요리가 조용히 순위에 포함되지 않는다.
- 관리자 이외의 사용자는 서버 데이터를 변경할 수 없다.
- PC와 390px 모바일에서 핵심 Playwright 흐름이 통과한다.
- 사용자 로컬 데이터 내보내기와 가져오기가 왕복 후 동일한 값을 복원한다.
